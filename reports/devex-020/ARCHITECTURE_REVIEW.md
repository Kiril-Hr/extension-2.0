## Rules and conditions

[GoogleMeetEventRuleService](../../devxtension/src/test/modules/googleMeetModule/services/secondaryServices/googleMeetEventRuleService.ts) dispatches on meeting titles and computes departure conditions using guests and leads. [GoogleMeetConditionService](../../devxtension/src/test/modules/googleMeetModule/services/secondaryServices/googleMeetConditionService.ts) combines predicates, timers and DOM clicks. [RulesIntermediaryService](../../devxtension/src/test/modules/intermediaryServices/services/rulesIntermediaryService.ts) fetches and parses configuration. Meet owns validation of its configuration and decisions about missing rules. Core can own cancellation of a registered timer while the feature still owns what it means to leave a meeting.

Propose ordinary consumer functions, e.g. `const shouldLeave = (meeting: Meeting) => rules.some(rule => rule(meeting))`, with the application defining the input and error policy. An independent library becomes worth evaluating when a second application needs the same evaluation and validation semantics. No rule dispatcher, server or business predicates proposed for Core.

## Author review disposition

The factory controller owns feature policy. Core passes an activation capability to opted-in consumers. The shared service remains an ordinary DI singleton. The approved resource boundary is one activation, with separate first/last ownership for shared widgets. Post-start control registration and explicit executor selection are accepted directions. A Core rule engine is deferred. The remaining gate covers the concrete signatures, opt-in syntax and compatibility cases in [the combined consumer example](FINAL_REPORT.md#combined-consumer-example).
